# 相談のモデルと推論の強さの比較

実施日: 2026-11-12

## はじめに

AI アシスタントに使うモデルと推論の強さを決めるため、gpt-6-luna の medium と high、gpt-6.1-terra の low と medium の 4 通りで、配信者の困りごと 7 件の相談を模して比べました。依頼者の決定では gpt-6.1-terra が本命で、推論の強さは low と medium から、この結果をもとに選びます。あわせて、Web 検索の取り込み量と費用の割合を見積もるため、gpt-6.1-terra の low から Web 検索の道具を外した構成も実行しました。

会話の全文は `docs/logs/2026-11-12-model-eval/outputs.md`、自動の集計は同じフォルダーの `stats.md` にあります。

## 検証方法

### 試験の道具

`tools/model-eval/main.cpp` の `aia-model-eval` で行いました。CMake のオプション `AIA_BUILD_MODEL_EVAL` でビルドします。道具の定義・指示文・要求の組み立て・応答の解釈には、プラグインと同じ `build_tools_json()`・`assistant_instructions()`・`build_request()`・`parse_response()` を使います。通信には `src/openai-client.cpp` を使います。OBS Studio は起動していません。

1 つの場面の会話は次のように進みます。

- 利用者の最初の発話を送ります。応答の出力のアイテムは、推論のアイテムを含めてすべて次の要求の input に足します。
- モデルが取得の道具を呼んだら、場面のファイルに用意した模した結果を返します。`limit_head` を通し、`read_log` だけは `limit_tail` を通します。`get_source_details` はソース名ごとに結果を用意し、無いソース名には `source not found` を返します。
- `change_settings` と `add_item` は `parse_change_settings` と `parse_add_item` で検査します。通れば利用者が承認して適用したという結果を返し、通らなければ誤りの説明を返します。出力と映像の設定は、場面で出力が稼働中なら止めるよう求める結果を返します。止まっていれば `classify_output_setting` で判定し、GuideOnly なら適用できないため設定画面の手順を案内するよう求める結果を返します。提案はすべて記録します。
- 適用した変更は、以後の取得の道具の結果に反映します。
- モデルが道具を呼ばずに文章で返答したら、場面に用意した利用者の返答を順に送ります。返答が尽きたら会話を終えます。1 つの場面で送る要求は 12 回までです。
- HTTP 429 と 5xx と通信の失敗は、5 秒と 10 秒の間を置いて 2 回まで送り直します。
- API キーは `.tmp/.env` の `OPENAI_API_KEY=` の行から読みます。画面・ログ・ファイルには出していません。出力のファイルにキーの文字列が含まれないことは、全ファイルの検索で確かめました。

### 場面

`.prompts/INIT.md` の配信者の困りごとの表の上位から 7 件を選びました。模した結果は OBS Studio 33.0.1 のログの書式と設定のキーに合わせました。場面のファイルは `tools/model-eval/scenarios/` にあります。

| 場面 | 利用者の最初の発話 | 正解の原因 | 期待する直し方 |
| --- | --- | --- | --- |
| 01-black-screen | 画面が真っ黒で何も映らないです | ノート PC で、OBS が NVIDIA の GPU、画面が Intel の GPU で動き、DXGI の複製が失敗している | 画面キャプチャの方式を Windows 10 (1903 以降) に変える。Windows のグラフィックスの設定で OBS を省電力の GPU にする |
| 02-game-audio | ゲームの音が配信に入ってないみたいです。自分には聞こえてます | デスクトップ音声が以前の Realtek のスピーカーに固定されている | デスクトップ音声のデバイスを USB ヘッドセットに変える |
| 03-mic-track | 配信してたらコメントで声が聞こえないって言われました。OBS のメーターは動いてるんですけど | 詳細出力で配信はトラック 1、マイクはトラック 2 だけ | マイクの音声トラックに 1 を足す |
| 04-echo | 視聴者さんから声が二重に聞こえるって言われます | マイクのモニタリングが「モニターと出力」で、スピーカーに出た声をデスクトップ音声が拾う | マイクのモニタリングを切る。配信中のため、すぐ視聴者に聞こえることを伝える |
| 05-encoding-lag | 配信がカクカクするって言われました。ゲームは普通に動いてます | x264 の medium で 1080p60 のエンコードが追いつかず 24.5% のフレームを飛ばした | エンコーダーの種類を NVENC に変える。この項目は案内に回す項目のため、設定画面の手順を案内する |
| 06-dropped-frames | 配信がよく止まるって言われる。なんで？ | Wi-Fi で上り約 8Mbps に対し映像ビットレートが 9,000kbps | 配信を止めてから映像ビットレートを下げる。有線にする |

各場面には、利用者の返答を 2 件か 3 件用意しました。場面 03・04・06 では配信中の状態から始まり、場面 06 では 2 件目の返答で配信を止めます。

### 判定

自動の判定は、場面のファイルの `judge` の基準で `aia-model-eval report` が行います。

- 原因の言及: アシスタントの文章に、場面ごとのキーワードの群がすべて含まれること
- 読むべき道具: 場面ごとに決めた取得の道具を呼んだこと
- 直し方の提案: 期待する `change_settings` か `add_item` の提案をしたこと
- 避けるべき提案: 場面ごとに決めた提案をしなかったこと。ミュートや出力の設定の変更などです
- 案内に回す項目の提案: `classify_output_setting` で GuideOnly になる項目を `change_settings` で提案した回数

会話を読んだ判断は、別に表にしました。判断の基準は、正解の原因を利用者に説明できたこと、直し方が正しいこと、指示文の決まりに従ったことです。

試験は 2 回実行しました。1 回目は、適用した変更を以後の取得の結果に反映していませんでした。そのため場面 01 では、モデルが変更の後に設定を読み直し、同じ変更を再び提案しました。場面 01 と 02 には、モデルの質問とかみ合わない利用者の返答もありました。2 回目は、変更を反映し、場面 01 と 02 の返答を直して実行しました。以下の結果は、通信の失敗の節を除いて 2 回目のものです。1 回目の生のログは追跡対象外の `.logs/2026111207-model-eval/` にあります。

判断の理由は次のとおりです。

- 01 の luna-high: キャプチャの方式を変えた後、2 回目の発話への要求が通信の失敗で 3 回とも終わりました。GPU の不一致の説明は出ていません。
- 01 のほかの構成: いずれも方式を Windows 10 (1903 以降) に変え、まだ映らないという返答の後に、ログの Intel と NVIDIA の GPU の違いを挙げて Windows のグラフィックスの設定の手順を案内しました。terra-low・terra-medium・luna-medium は Web 検索で OBS の公式の GPU 選択のガイドを出典に付けました。terra-low-noweb は、GPU が別であることを「原因かもしれません」と述べ、ログの GPU 名は挙げませんでした。
- 04 の luna の 2 構成: どちらもモニタリングを切る提案は正しく行いました。原因の説明は、デスクトップ音声による再取り込みではなく、スピーカーの音をマイクが拾う経路でした。luna-medium の説明は次のとおりです。

> 「マイク」のモニターをオフにしました。配信へのマイク音声はそのままで、スピーカーから自分の声が再生されてマイクに入り直す経路を止めています。

- 04 の terra の 3 構成: 提案の理由に、デスクトップ音声へ重複して入ることを書きました。terra-low の理由は次のとおりです。

> マイクの声がスピーカーから再生され、デスクトップ音声に重複して入るのを防ぐためです。

指示文の決まりへの従い方で、構成による違いが出た箇所は次のとおりです。

- 配信中に音量やモニタリングを変えるときは、視聴者にすぐ聞こえることを伝える決まりがあります。場面 04 で、luna-high と terra-medium は伝えました。luna-medium・terra-low・terra-low-noweb は伝えませんでした。場面 03 の音声トラックの変更では、5 つの構成すべてが提案の理由か返答で伝えました。
- 場面 06 では、5 つの構成すべてが配信中に出力の設定を提案せず、止めるよう求めました。止めたという返答の後は、すべての構成が `get_obs_status` で状態を読み直してから `SimpleOutput/VBitrate` の変更を提案しました。値は luna-high が 5,000、ほかが 4,500 です。
- 場面 05 では、5 つの構成すべてがエンコーダーの種類を `change_settings` で提案せず、設定画面の手順を案内しました。terra-medium は Web 検索を 1 回行い、OBS の公式のハードウェアエンコードの記事を出典に付けました。luna-high は手順の最後に「統計の「エンコード遅延」が増えるか確認してください」と書き、増減を取り違えました。

## 考察

### 推論の強さ

gpt-6.1-terra は low で足りると考えています。7 つの場面で、low と medium はどちらも原因を正しく説明し、直し方も正しく、指示文の決まりにも従いました。low は medium より応答の中央値が約 1.3 秒短く、1 回の相談の費用も平均で約 0.004 米ドル安くなりました。

low の弱さとして見えたのは 2 点です。場面 02 では、ヘッドセットの機種を 2 回確かめてから提案し、medium より利用者の返答が 1 回多く必要でした。場面 04 では、配信中にモニタリングを変えるときに視聴者にすぐ聞こえることを伝えませんでした。前者は承認の画面があるため実害は小さいと考えています。後者は指示文の決まりへの違反で、medium では起きていません。ただし 1 件ずつの観測で、場面 03 では low も伝えています。推論の強さの差によるものとは言い切れないと考えています。

medium は low より Web 検索が多く、検索のある応答には出典が付きました。場面 05 のように、検索しなくても答えられる場面でも検索しています。検索の多さが答えの正しさの差にはつながっていないと考えています。

### gpt-6-luna

gpt-6-luna で十分とは読めないと考えています。1 回の相談の費用の平均は gpt-6.1-terra-low の約 9% から 35% でしたが、gpt-6.1-terra-low でも 1 回の相談は平均 0.0116 米ドルで、最大でも 0.06 米ドル未満でした。一方で gpt-6-luna には次の弱さがありました。

- 場面 04 で、medium も high も原因の仕組みを取り違えました。直し方は正しいため、この場面では実害はありませんが、仕組みの説明を誤ると、利用者が次の手を誤る可能性があると考えています。
- 推論のトークンが gpt-6.1-terra より多く、応答の中央値は terra-low より 0.8 秒から 1.8 秒長くなりました。
- 通信の失敗が gpt-6-luna の要求だけで起きました。

通信の失敗の原因は、この試験では特定できませんでした。1 回の失敗が 10 秒から 21 秒で終わっていることから、要求全体の上限ではなく接続の段階の上限に当たった可能性があると推測します。ただし接続の段階の失敗であれば、モデルの違いで起き方が変わる理由が説明できません。場面 01 の後半に偏っている理由も分かっていません。

### Web 検索

Web 検索の費用の大部分は検索 1 回の料金の 0.01 米ドルで、取り込みの費用はその半分程度と考えています。検索 1 回の取り込みは 4,700 から 6,100 トークン程度でした。gpt-6.1-terra の入力の単価では 0.005 から 0.006 米ドルに当たります。

道具を入れるだけで要求ごとに 4,436 トークンが上乗せされる点は、圧縮の閾値の設計に関わると考えています。上乗せは毎回の input_tokens に含まれるため、圧縮を勧める閾値の 10 万トークンの約 4% を占めます。キャッシュに載るため、費用への影響は 7 件で 0.009 米ドル程度と小さいと考えています。

### 試験の限界

利用者の返答は場面ごとに決めた列で、モデルの質問に合わせて変わりません。直し方を 1 回で当てたモデルにも、まだ真っ黒ですと返す場面があります。この形の試験は、原因の当たり外れと道具の選び方の比較には使えますが、会話の長さや聞き返しの回数の比較には向かないと考えています。
